> how does git work? Also explain the workflow and relevant commands.           

● How Git Works

  Git is a snapshot-based version control system. Every commit is a snapshot of
  all tracked files at that moment, plus a pointer to the previous commit —
  forming a chain (the history).

  A ← B ← C ← D   (main)
           ↑
           └── E ← F   (feature-branch)

  Key concepts:
  - Repository — the .git/ folder stores everything (all branches, history,
  objects)
  - Working tree — the actual files you see/edit
  - Staging area (index) — a holding zone for changes you're about to commit
  - HEAD — pointer to the current branch/commit you're on

  ---
  The Three States

  Working Tree  →  Staging Area  →  Repository
    (edit)        (git add)        (git commit)

  ---
  This Repo's Specific Workflow

  main (source code)         gh-pages (built output)
       │                            │
       ├── src/                     ├── assets/
       ├── package.json             └── index.html
       └── vite.config.ts
            │
            │  npm run build
            ▼
           dist/  ──────────────────► pushed to gh-pages
                                     GitHub serves this

  Step-by-step workflow:

  1. Do source work on main:
  git checkout main
  # edit files in src/
  git add src/SomeFile.ts
  git commit -m "Add feature X"

  2. Build the project:
  npm run build        # Vite outputs to dist/

  3. Push built files to gh-pages:
  git checkout gh-pages
  # copy dist/ contents here, then:
  git add assets/ index.html
  git commit -m "Deploy build"
  git push origin gh-pages

  4. Push source changes too:
  git checkout main
  git push origin main

  ---
  Branches = Cheap Pointers

  A branch is just a named pointer to a commit — switching branches instantly
  moves HEAD and updates your working tree to that snapshot. No files are
  duplicated on disk; git stores them efficiently as objects.

  For this repo specifically, main and gh-pages have completely different file 
  trees — that's why checking out between them changes what files you see
  entirely.

● This is a pure static React/Vite app — no backend. Railway works, but you need

  ---
  Step-by-Step: Deploy to Railway

  1. Fix the base path

  In vite.config.ts, change base:
  // For Railway (root URL), use:
  base: '/',

  // Keep '/2Dlayout/' only for GitHub Pages

  You can make this conditional later, but for now just set it to /.

  ---
  2. Sign up & connect GitHub

  - Go to railway.app → Sign up with GitHub
  - Click New Project → Deploy from GitHub repo
  - Select this repo (2Dlayout)

  ---
  3. Configure the service

  Railway will auto-detect Node.js. Set these in Settings → Deploy:

  ┌────────────────┬─────────────────┐
  │    Setting     │      Value      │
  ├────────────────┼─────────────────┤
  │ Build Command  │ npm run build   │
  ├────────────────┼─────────────────┤
  │ Start Command  │ npm run preview │
  ├────────────────┼─────────────────┤
  │ Root Directory │ (leave empty)   │
  └────────────────┴─────────────────┘

  The vite preview command already has host: '0.0.0.0' and port: 8080 in your
  config — Railway picks those up automatically.

  ---
  4. Set environment variables (if needed)

  This app has no .env usage currently, so skip this step.

  ---
  5. Deploy

  Railway auto-deploys on every push to main. Watch the build logs in the
  dashboard. When done, Railway gives you a URL like
  https://your-app.railway.app.

  ---
  6. Custom domain (optional)

  Settings → Networking → Custom Domain — point your DNS CNAME to Railway's
  provided hostname.

  ---
  Heads Up

  - Railway has a $5/month hobby plan (free trial credits available but expire)
  - For a pure static app like this, GitHub Pages is free and already set up —
  Railway makes more sense if you later add a backend/API
  - If you want Railway for free with static sites, Netlify or Vercel are better
   alternatives

  git add src/

● Searched for 1 pattern (ctrl+o to expand)

● This URL has 3 separate layers — here's how each piece is set up:

  ---
  https://internal-calculator.megaresistors.com/#motorsizing

  Layer 1: megaresistors.com — the domain

  Owned by your org, managed in a DNS provider (Cloudflare, Route53, etc.)

  Layer 2: internal-calculator — the subdomain

  Your org's IT/DevOps adds a DNS CNAME record:
  internal-calculator.megaresistors.com  →  CNAME  →  your-app.railway.app
  Then in Railway: Settings → Networking → Custom Domain, they enter
  internal-calculator.megaresistors.com. Railway handles the SSL cert
  automatically.

  Layer 3: /#motorsizing — the hash fragment

  This is client-side only — the browser never sends the #... part to the
  server. It's used by React apps for routing between "pages" without a full
  page reload.

  Server sees:   GET /
  Browser sees:  /#motorsizing  →  React renders "Motor Sizing" tool

  This means your app (or a future umbrella app) uses hash-based routing to show
   different calculators under one domain. Example:
  /#motorsizing     → Motor Sizing tool
  /#cabletray       → Cable Tray calculator
  /#2dlayout        → this app (2D layout)

  ---
  How the full flow works

  User visits:  https://internal-calculator.megaresistors.com/#motorsizing
                          │                                       │
                          ▼                                       │
                DNS: CNAME → railway.app                         │
                          │                                       │
                          ▼                                       │
                Railway serves index.html ◄──────────────────────┘
                          │                    (hash never leaves browser)
                          ▼
                React reads window.location.hash → renders Motor Sizing

  ---
  What you need to do for THIS app

  In vite.config.ts, set base: '/' (already covered). Your org's DevOps handles
  the DNS and Railway custom domain setup. You just push code to main.

  If the org wants this app at /#2dlayout, they'd wrap multiple tools in a
  single React app with a hash router — or deploy each tool as its own Railway
  service under a different subdomain.

> Layer 2 need to be set up by whom who can update DNS CNAME, correct?          

● Yes. Whoever has login access to the DNS provider (Cloudflare, Route53,
  GoDaddy, etc.) where megaresistors.com is registered/managed.

  Typically in an org that's:
  - IT/DevOps team — most common
  - Domain admin — whoever originally set up the domain

  You'd ask them to add:
  Type:  CNAME
  Name:  internal-calculator
  Value: your-app.up.railway.app

  Then you handle the Railway side yourself (adding the custom domain in Railway
   settings). Both have to be done — DNS points traffic to Railway, Railway
  accepts it.
